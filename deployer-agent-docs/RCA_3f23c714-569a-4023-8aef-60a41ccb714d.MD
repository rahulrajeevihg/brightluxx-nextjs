# RCA — Deploy run 3f23c714-569a-4023-8aef-60a41ccb714d (nextjs-revamp-2)

## Summary
The deploy fails at the **build_image** step, during `next build`. It is a **source-level** failure in the app code, not a deployment/manifest problem. It has reproduced **identically across all 4 initial-deploy attempts** (3f23c714, 1de0b82d, 621ba791, 1ae9abdf).

## Root cause
The app renders **241 pages as static (SSG)** at build time. The route `/luxury-home-cinema` (and almost certainly the other data-driven routes in the same group) performs a server-side `fetch()` to a backend/API endpoint **during prerendering**. Inside Cloud Build there is **no backend process and no database running**, so the connection is refused (`ECONNREFUSED`) and `next build` aborts.

This is inherent to how the pages are written — they do network data-fetching at build time against a service that only exists at runtime. No deployment manifest, tier, or secret change can make a backend reachable during the static-export phase, so this must be fixed in the application source.

## Reproduction note
I attempted to reproduce in the eph sandbox but it was **unavailable** (envcore returned `container not found` / `cannot exec in a deleted state` on 3 consecutive spawn attempts), so I could not run `next build` in-pod. The diagnosis is nonetheless **high-confidence**: the failure is deterministic, identical across 4 runs, and the error message pinpoints the page, the operation (`fetch`), and the cause (`ECONNREFUSED` at static generation).

## Recommended fix (E1 applies in the source)
Stop prerendering the data-fetching routes at build time. Pick whichever fits the app:

1. **Opt the affected route(s) out of static generation** — add to `src/app/luxury-home-cinema/page.tsx` (and every sibling route that fetches backend data at build time):
   ```ts
   export const dynamic = 'force-dynamic';   // render at request time, not build time
   // or, to keep caching but avoid build-time prerender:
   // export const revalidate = 0;
   ```
2. **Preferred, if the page is a Server Component fetching its own API over HTTP:** replace the `fetch('<url>/api/...')` call with a **direct data-layer / DB query** (call the function that talks to Mongo directly) instead of an HTTP round-trip. A Server Component fetching its own API route during build is the classic cause of this exact `ECONNREFUSED`.
3. If the 241 pages come from a dynamic segment with `generateStaticParams`, either make that segment dynamic (`export const dynamicParams = true` + `dynamic = 'force-dynamic'`) or guard `generateStaticParams`/the fetch so it tolerates an unreachable backend at build time (return `[]` / skip the fetch when the backend isn't up).

After the source fix, **E1 should re-trigger the deploy** — a plain redeploy of the current (still-broken) source will fail the build identically.

## Not the cause
- Not a manifest/Dockerfile issue — compile + TypeScript passed (`✓ Compiled successfully`), failure is purely the runtime data-fetch during static export.
- Not a tier/OOM issue — process exited on a fetch error, not a kill.
- Not a secrets issue that the deployer can set — no backend is running during build regardless of env values.
