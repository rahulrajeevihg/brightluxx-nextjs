# RCA — Deploy run 621ba791-bf4b-4689-b8d9-8a660f7189b8 (nextjs-revamp-2)

## Verdict
**Source-level build failure. Not a manifest/platform issue.** `create_deployment_manifest` / `resume_pipeline` cannot fix it — the fix is in the app's Next.js source and must be applied by E1 in the preview environment, then redeployed.

## Failed step
`build_image` (Cloud Build) → `yarn build` → `next build`. Both initial attempts (1ae9abdf… and 621ba791…) failed identically at the same page.

## Root cause
Next.js (16.3.2, App Router) **statically prerenders pages at build time**. The build compiled and type-checked successfully, then failed while generating static pages (it was generating 241 pages across 7 workers):

```
Error occurred prerendering page "/luxury-home-cinema".
[TypeError: fetch failed] { digest: '3227098399',
  [cause]: AggregateError: ... code: 'ECONNREFUSED' }
Export encountered an error on /luxury-home-cinema/page: /luxury-home-cinema, exiting the build.
⨯ Next.js build worker exited with code: 1
```

`ECONNREFUSED` = the page's server component (or its `generateStaticParams` / data loader) calls `fetch()` to the backend/API **during the build**. At build time there is no backend/Mongo/API listening (the deploy build container only runs `next build`; the FastAPI/Mongo services are not up), so every such fetch is refused and the prerender of that route throws, aborting the whole build.

This is a build-time vs request-time data-fetching problem, not a missing dependency, env var, or resource limit. `/luxury-home-cinema` is simply the first data-backed route the workers hit; any statically-prerendered route that fetches live data will fail the same way.

## Fix (apply in source, pick one — in order of preference)
The data-fetching routes must not hit the network during `next build`. Options:

1. **Opt the data-backed routes out of static prerendering** so they render at request time (when the backend IS up). In the affected `page.tsx` (and sibling dynamic routes under the same segment):
   ```ts
   export const dynamic = 'force-dynamic';
   ```
   (or `export const revalidate = 0;`). This defers the `fetch` to request time.

2. **If these routes use `generateStaticParams` to pre-build many paths**, either remove the build-time param generation (let them render on-demand with `export const dynamicParams = true`), or make `generateStaticParams` return `[]` so nothing is prerendered.

3. **Make the fetches build-safe** — wrap the data loader in try/catch and return a fallback/empty payload when the fetch fails, so a prerender never throws. Less ideal: it ships empty static pages if the backend is ever unreachable.

Recommended: option 1 for the affected segment(s). The 241 generated pages suggest a templated/dynamic route group (e.g. `[slug]`), so apply the opt-out at that route segment, not just the one page.

## What to verify after the fix
`yarn build` completes locally in preview with the backend NOT running (that reproduces the build-container condition). Then redeploy.
