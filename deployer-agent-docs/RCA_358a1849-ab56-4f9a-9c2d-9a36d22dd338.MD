# RCA — Brightluxx / `nextjs-revamp-2` production publish failures

## TL;DR
The `force-dynamic` fix **worked**. The repeated `/luxury-home-cinema` prerender/ECONNREFUSED failure is **gone**. The deploy now fails **later and for a new reason**: the Docker *runner* stage cannot find `/app/.next/standalone`, because `next.config.ts` does not set `output: 'standalone'`. This is **not** a credits problem and **not** a missing `API_ORIGIN` problem.

## Answers to the specific questions

### 1. Credits vs. real build failure
**Not credits.** Every recent attempt actually downloads source and RUNS the build. The CodeBuild phases complete `DOWNLOAD_SOURCE → INSTALL → PRE_BUILD → BUILD`, `yarn install` succeeds, and it reaches the `yarn build` / Docker stages. The earlier "50 ECU vs 42.01 available" block is **not** what these runs are hitting. The build is executing to completion and failing on app content, not on a pre-start credit gate.

### 2. Does it still fail on /luxury-home-cinema? Is the fix in the built source?
**The fix IS present and effective.** In the latest run (`358a1849-ab56-4f9a-9c2d-9a36d22dd338`), `next build` ran to completion — no `/luxury-home-cinema` error, no `ECONNREFUSED`, no prerender error at all. The build now fails one stage LATER, in the Docker image assembly:

ERROR: failed to solve: ... "/app/.next/standalone": not found

That class of failure no longer occurs on the current source. So: the pipeline is now building the up-to-date snapshot WITH the `force-dynamic` fix, and that fix resolved the prerender crash.

### 3. Is API_ORIGIN (and other env) configured in the build?
**`API_ORIGIN` is present at build time.** `next.config.ts` executes successfully in every build:
```
#15 ✓ Running next.config.ts took 37ms
- Environments: .env
```
If `API_ORIGIN` were unset, your guard (`if (!process.env.API_ORIGIN) throw new Error('API_ORIGIN must be configured')`) would have thrown right there and the build would die at "Running next.config.ts". It did not — so `API_ORIGIN` is set in the build `.env`. (Note the build-time `.env` rewrite sets the backend URL to `https://nextjs-revamp-2.internal.aws.emergent.host`.)

The backend-only secrets (`MONGO_URL`, `DB_NAME`, `CORS_ORIGINS`, `EMERGENT_LLM_KEY`, `ADMIN_SEED_PASSWORD`, `JWT_SECRET`) could **not** be verified: `list_secrets` is scoped to the active run, and this deployment has no active run (it has never successfully promoted), so it returns `no_active_run`. Their presence on the failed runs is not inspectable from here.

### 4. Is the backend deployed/served in prod? What should API_ORIGIN point to?
**Important architectural flag.** The deployment template is `nextjs_mongo_shadcn_base_image` — the **Next.js-only** template (single Next.js app, `node server.js`, nginx disabled, NO Python process). The build is purely `yarn install` + `next build`, and the runner image copies only `.next/standalone`, `.next/static`, and `public`. There is **no FastAPI/uvicorn in this image**. So under the current template a separate FastAPI backend on `:8001` is **not built and not served** in production.

Consequences for E1 to resolve:
- If the Next.js app genuinely needs the FastAPI backend, this app is on the wrong template. The Next.js+FastAPI variant is `nextjs_fastapi_mongo_base_image`. Staying on `nextjs_mongo_shadcn_base_image` means `API_ORIGIN`/`/api/*` rewrites have nothing to reach in prod even once the build succeeds.
- If the app is meant to be Next.js-only (API routes handled inside Next.js), then `API_ORIGIN` should be removed/made optional and the separate backend dependency dropped.
- Nothing is currently deployed (deployment_status = failed, no active run), so there is no live backend URL today.

## Primary blocker & minimal fix (Code — E1 applies in source)
**Cause:** The platform Next.js template Dockerfile does `COPY --from=builder /app/.next/standalone ./`, which requires Next.js standalone output. `next build` only emits `.next/standalone` when the config opts in. The current `next.config.ts` does not, so the directory is absent and the COPY fails.

**Fix:** add `output: 'standalone'` to `next.config.ts`:
```ts
const nextConfig = {
  output: 'standalone',
  // ...existing config (rewrites, API_ORIGIN guard, etc.)
};
export default nextConfig;
```
Then redeploy. A local `yarn build` after this change should produce `.next/standalone/` — confirm that directory exists before redeploying.

**Verification note:** This could not be reproduced in an eph sandbox — pod boot failed repeatedly (`eph_spawn_failed`, "pod reached terminal phase Failed before becoming Running"). Diagnosis is from build-log evidence, which is unambiguous (`COPY .next/standalone → not found`) and matches the standard Next.js standalone-output contract the template enforces.

## Sequence after the fix
1. Add `output: 'standalone'` → redeploy. This clears the current `#16` runner failure.
2. Separately decide the backend question in #4 (correct template vs. Next.js-only) so `API_ORIGIN`/`/api/*` actually resolves in prod at runtime.
