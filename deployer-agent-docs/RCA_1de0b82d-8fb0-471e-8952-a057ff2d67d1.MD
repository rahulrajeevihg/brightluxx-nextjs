# RCA — Deploy build failure (nextjs-revamp-2)

## Summary
The deploy fails at the **build_image** step while running `next build`. Next.js
statically prerenders 241 pages; page **`/luxury-home-cinema`** performs a
**server-side `fetch()` at build time** that cannot connect to its backend/API
(`TypeError: fetch failed` → `cause code: ECONNREFUSED`), which aborts the whole
build.

This is a **source-level fault**, not a deployment/manifest problem. It is
deterministic: runs `1ae9abdf-bee0-4dc4-8a7d-040a06573fe0`,
`621ba791-bf4b-4689-b8d9-8a660f7189b8`, and `1de0b82d-8fb0-471e-8952-a057ff2d67d1`
all failed on the exact same page with the exact same error.

## Root cause
Template: `nextjs_mongo_shadcn_base_image` (Next.js, `frontend_type: kubernetes`).
During Cloud Build **only the app image is built — there is no running backend,
MongoDB, or API server**. The route `/luxury-home-cinema` (and likely other
data-dependent routes) is treated as a **statically-generated (SSG) page** and
executes a `fetch()` to the backend at build time. That endpoint is not
reachable during the build (`ECONNREFUSED`), so prerendering throws and
`next build` exits non-zero.

Note: the build got to 180/241 before failing — the other pages either don't
fetch or tolerate failure; `/luxury-home-cinema` does a hard build-time fetch.

## Fix (Code — applied by E1 in the source repo, then re-trigger deploy)
Make the data-dependent route(s) render at request time instead of being
prerendered at build time. Any ONE of the following on the affected page(s)
(start with `app/luxury-home-cinema/page.*`, and apply to any sibling route that
does a build-time server fetch):

1. **Preferred — opt the page out of build-time prerendering:**
   ```ts
   // top of app/luxury-home-cinema/page.tsx (and similar data-fetching pages)
   export const dynamic = 'force-dynamic';
   ```
   The page then renders on-demand at runtime, when the backend IS available.

2. **Or** make the build-time fetch non-fatal (so a failed fetch yields fallback
   data instead of aborting the build):
   ```ts
   let data = null;
   try {
     const res = await fetch(url, { cache: 'no-store' });
     if (res.ok) data = await res.json();
   } catch {
     data = null; // render with empty/fallback data; don't crash the build
   }
   ```

3. **Or**, if the route is generated via `generateStaticParams`, stop
   pre-generating these params at build time (return `[]` / rely on
   `dynamicParams = true`) so they are rendered on first request.

Also verify the fetch target URL is a runtime value (e.g. the backend service
URL from env), not `localhost`/preview — a `localhost` target will never resolve
inside Cloud Build or the production pod's build phase.

## Why not a manifest fix / retry
The build step (`yarn build`) and all manifests are correct. The failure is in
app code that runs during `next build`. A manifest edit + `resume_pipeline`, or a
plain retry, would rebuild the identical source and fail at the same page — as
the three identical prior failures confirm. No pipeline re-run will fix this
until the source changes.

## Verification status
Diagnosed from Cloud Build logs (deterministic, reproduced across 3 runs). The
eph sandbox could not be spawned (platform infra error:
`eph_source_check_failed` — container repeatedly entered a deleted state on every
retry), so this was not independently reproduced in-pod. Reproduction would add
little regardless: the sandbox has no backend/secrets, so the same build-time
`fetch()` would fail with the same `ECONNREFUSED`.
